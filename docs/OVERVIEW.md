# Что было сделано и почему

Документ для владельца проекта: что не так было со старым кодом, что его
заменило и какие решения приняты по дороге. README отвечает на вопрос
«как запустить», этот файл — на вопрос «почему так, а не иначе».

---

## 1. Что было

Прототип из трёх частей:

* `backend/main.py` — FastAPI с двумя ручками: список матчей и вход;
* `frontend/` — приложение на Create React App с тремя компонентами;
* `db_init.sql` — схема базы, которую надо было накатывать вручную.

Как доказательство работоспособности идеи — нормально. Как фундамент —
нет, и вот почему.

### Проблемы схемы базы

| Что было | Чем плохо |
| --- | --- |
| `matches.score_team1 INT DEFAULT 0` | Нельзя отличить «матч не сыгран» от «сыграли 0:0». Нет статуса матча вообще. |
| Голы и в `goals`, и в `match_players.goals` | Два источника правды. При первой же правке результата они разъедутся, и никто не узнает, какой верный. |
| В `goals` только автор и минута | Нет ассистента, автогола, пенальти. Карточки хранились счётчиками, а не событиями — по ним нельзя восстановить, на какой минуте что было. |
| Ни одного `UNIQUE` и `CHECK` | Команду можно дважды заявить в турнир, матч можно создать «Мехмат против Мехмата». |
| `players.age INT` | Возраст протухает через год. Он вычисляется из даты рождения, хранить его незачем. |
| `faculty VARCHAR(3)`, `msu_status VARCHAR(3)` | Трёхбуквенные коды вместо справочника. Через полгода никто не вспомнит, что значит `ФББ` против `ФБИ`. |
| Нет таблицы пользователей | Роль была зашита в токен константой, аккаунт один на всех. |
| Нет туров, стадий, стадионов, назначения судей | Всё, из чего состоит расписание реальной лиги. |
| Нет истории изменений | Судья внёс результат, кто-то поправил — следов не остаётся. Для лиги это принципиально. |

### Проблемы бэкенда

* `except:` в проверке токена ловил в том числе собственную ошибку «доступ
  запрещён» и превращал 403 в 401 — то есть сообщение о правах подменялось
  сообщением о входе.
* В JWT не было срока жизни: выданный токен работал вечно.
* Логин — один захардкоженный `admin` с общим паролем из переменной окружения.
* `add_match` возвращал результат `database.execute()` как идентификатор
  созданного матча; без `RETURNING` это не идентификатор.
* `metadata.reflect()` выполнялся при импорте модуля: если база недоступна,
  приложение не запускалось вообще.
* Не было миграций — схему приходилось катать через удаление всей базы.

### Проблемы фронтенда

* Create React App больше не поддерживается, с React 19 это тупик.
* Нет серверного рендеринга — плохо для поиска и для скорости на телефоне.
* Список матчей показывал «Team 1 vs Team 2», потому что API не отдавал
  названий команд.
* В форме админа была кнопка входа с логином и паролем `admin`/`admin`
  прямо в исходниках.

Вывод: идеи в схеме были правильные, реализация — сырая. Дешевле переписать,
чем чинить, поэтому переписано полностью.

## 2. Что теперь

Одно приложение на **Next.js 15 + TypeScript**, база **PostgreSQL** через
**Prisma**, оформление на **Tailwind**. Один язык, одна команда запуска,
один деплой.

### Главное архитектурное решение

**Единственный источник правды — таблица событий матча `MatchEvent`.**

Счёт матча, турнирная таблица, бомбардиры, карточки, статистика игрока и
команды нигде не хранятся готовыми числами. Они выводятся из событий:

```
события матча  →  счёт матча  →  турнирная таблица
              ↘   статистика игроков и команд
```

Что это даёт на практике: судья исправляет минуту гола или удаляет
ошибочно записанный мяч — счёт, таблица и список бомбардиров меняются сами
и сразу, согласованно. Расхождение между «в таблице 12 очков, а по матчам
получается 11» физически невозможно.

Цена решения — статистика считается запросом, а не берётся готовой. Для
университетской лиги это тысячи строк, база отвечает мгновенно. Если
турниров станет в сотни раз больше, здесь появится кеширование —
но не раньше, чем это понадобится.

### Что ещё изменилось в данных

* **У матча есть статус**: назначен, первый тайм, перерыв, второй тайм,
  доп. время, пенальти, завершён, перенесён, отменён, техпоражение.
  Счёт `null` означает «не игрался» и отличается от 0:0.
* **Заявка привязана к паре «команда + турнир»** (`RosterEntry`), а не к
  команде вообще. Игрок может за сезон сменить команду, и статистика
  прошлых турниров при этом не переписывается задним числом.
* **Игровые часы хранятся как момент старта тайма плюс накопленные секунды.**
  Поэтому минута на табло одинаковая у всех зрителей, переживает
  перезагрузку страницы и не зависит от того, у кого какие часы.
* **Ограничения на уровне базы**: команда не играет сама с собой, минута
  события в разумных пределах, игрок не ассистирует сам себе, номер от 1 до 99,
  дата окончания турнира не раньше начала. Эти правила защищают данные,
  даже если кто-то полезет в базу напрямую через `psql`.
* **Журнал изменений** `AuditLog`: кто, что и когда поменял.
* **Убраны** таблицы `transfers` и `players_teams`. История «за кого играл»
  полностью восстанавливается из заявок по турнирам, а две таблицы,
  описывающие одно и то же, — источник будущих расхождений.

### Роли и доступ

Четыре роли: организатор, судья, капитан, зритель. Проверка идёт в два слоя:

1. `src/middleware.ts` — отсекает посторонних до отрисовки страницы, смотрит
   на роль в токене;
2. каждая страница и каждое серверное действие проверяет права ещё раз по
   базе — потому что middleware знает роль, но не знает, назначен ли этот
   судья именно на этот матч.

Пароли хранятся хэшами (bcrypt), сессия — подписанный JWT в httpOnly-куке
со сроком жизни неделю. При неверном логине пароль всё равно проверяется
против фиктивного хэша, чтобы по времени ответа нельзя было определить,
существует ли такой email.

### Консоль судьи

Отдельный интерфейс под телефон, потому что это основной сценарий:
судья стоит на поле с телефоном в руке.

* Кнопки хода матча ведут по сценарию: начать → перерыв → второй тайм →
  завершить. Показываются только те, что уместны сейчас.
* Кнопка «Гол» под каждой командой открывает окно с уже подставленной
  текущей минутой. Дальше — крупная сетка игроков: касание по автору,
  при желании по ассистенту, «Записать».
* Карточки, замены, автоголы, промахи с пенальти — там же.
* Любое событие в протоколе открывается касанием: можно поменять минуту,
  игрока, тип или удалить. Счёт пересчитывается автоматически.
* Матч правится и после финального свистка — можно дозаполнить протокол
  вечером, как и просили.

Состав на матч необязателен: если он не заполнен, выбирать можно любого
игрока из заявки. Иначе судья, забывший отметить состав, не смог бы
записать вообще ничего.

### Публичная часть

Ориентир — sofascore: лента дат сверху, матчи сгруппированы по турнирам,
строка матча одинаковая везде. Страница матча во время игры обновляется
сама раз в 20 секунд (обновление встаёт на паузу, если вкладка неактивна),
минута на табло тикает. Есть светлая и тёмная темы, всё время показывается
московское — независимо от того, где стоит сервер и где находится зритель.

## 3. Как проверялось

Проверки прогонялись на живом сервере против настоящей базы:

* **34 страницы** под всеми ролями отдаются со статусом 200; закрытые
  разделы редиректят на вход; судья не может открыть чужой матч; капитан
  не попадает в админку и в раздел судьи.
* **Полный сценарий матча через настоящие серверные действия** — 31 проверка:
  сохранение составов, старт, гол с передачей, автогол (засчитался
  сопернику), пенальти, замена, перерыв, второй тайм, правка события с
  пересчётом счёта, удаление события с пересчётом, завершение, запись
  в журнал.
* **Отклоняются** попытки записать: игрока другой команды, пас самому себе,
  минуту 999, замену без второго игрока, состав больше 11 человек.
* **Согласованность**: счёт совпадает с событиями во всех 32 сыгранных
  матчах демонстрационной базы.
* **Ограничения базы** проверены попыткой нарушить их напрямую через Prisma.

По ходу проверки нашлась и была исправлена ошибка в форме админки: сброс
полей после успешной отправки вызывался прямо во время отрисовки и уходил
в бесконечный цикл.

Временные тестовые файлы удалены — в репозитории их нет.

## 4. Что осознанно не сделано

| Чего нет | Почему |
| --- | --- |
| Загрузка файлов | Логотипы команд и фото игроков задаются ссылкой. Загрузка требует решения, где хранить файлы, — это зависит от выбранного хостинга. |
| Автоматическая сетка плей-офф | Кубковые матчи создаются вручную. Стадии в схеме уже есть, автоматика добавится, когда станет понятен регламент кубка. |
| Автоматические дисквалификации | Карточки считаются, но пропуск матча за перебор карточек не начисляется — это чисто регламентное правило, и оно у каждой лиги своё. |
| Уведомления | О начале матча, о результате. Требует решения про почту или Telegram. |
| Статистика судейства | Публичная страница судьи с его матчами. |

## 5. Куда смотреть в коде

Начинать стоит с трёх файлов — в них вся суть:

* `prisma/schema.prisma` — модель данных с комментариями;
* `src/lib/football.ts` — вся футбольная логика: подсчёт счёта из событий,
  построение турнирной таблицы, игровые часы, словари названий;
* `src/server/match-actions.ts` — запись протокола матча с проверками прав
  и пересчётом счёта.

Подробная карта проекта — в `CLAUDE.md` и `README.md`.

Старые материалы сохранены в `docs/legacy/`: прежняя схема в SQL и drawio,
дамп старой базы.
