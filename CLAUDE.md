# CLAUDE.md

Указания для Claude Code при работе с этим репозиторием.

## О проекте

Сайт студенческих футбольных турниров МГУ: расписание, результаты, турнирные
таблицы, статистика игроков. Судьи ведут протокол матча с телефона по ходу игры.

Единое приложение: **Next.js 15 (App Router) + TypeScript + PostgreSQL + Prisma +
Tailwind 4**. Отдельного бэкенда нет — запись в базу идёт через серверные действия.

Интерфейс и комментарии в коде — **на русском**. Придерживайся этого.

## Команды

```bash
npm run dev          # разработка, http://localhost:3000
npm run build        # production-сборка (включает prisma generate)
npm start            # запуск собранной версии
npm run typecheck    # tsc --noEmit — быстрая проверка перед сборкой
npm run db:seed      # перезаполнить базу демо-данными (СНОСИТ все данные)
npm run db:studio    # визуальный просмотр базы
npx prisma migrate deploy   # применить готовые миграции
npm run db:migrate          # создать новую миграцию после правки schema.prisma
```

ESLint в проекте не настроен. Проверка качества — `npm run typecheck` и
`npm run build`.

**Не запускай `next build`, пока работает `next dev`** — они пишут в один
каталог `.next`, dev-сервер после этого отдаёт 500. Сначала остановить,
потом собирать.

## Архитектура: главное правило

**Единственный источник правды по матчу — таблица `MatchEvent`.**

Счёт матча, турнирная таблица, бомбардиры, статистика игроков и команд
**нигде не хранятся готовыми числами** — они выводятся из событий.

Из этого следует:

* Любое изменение событий обязано проходить через `recalcScore()` в
  `src/server/match-actions.ts`. Не обновляй `Match.homeScore` / `awayScore`
  напрямую в обход этой функции.
* Не добавляй в схему денормализованные счётчики (голы игрока, очки команды).
  Если расчёт станет медленным — добавляй кеш, а не второе место хранения.
* Автогол записывается на команду **автора**, а засчитывается сопернику.
  Логика в `scoreFromEvents()` (`src/lib/football.ts`) — не дублируй её.

Второе правило: **`Match.homeScore === null` означает «матч не игрался»**.
Ноль — это сыгранный матч с нулём голов. Не путай и не подставляй `0` по умолчанию.

Третье: **`Match.homeTeamId` может быть `null`** — у матча плей-офф, созданного
заранее, участник ещё не определился. Любой новый код, читающий команды матча,
обязан это учитывать; подпись слота даёт `slotLabel()` из `src/lib/playoff.ts`.
Подстановкой занимается `resolvePlayoffSlots()` (`src/server/playoff.ts`), и она
не только заполняет слоты, но и **очищает** их, если результат-источник откатили.
Не вызывай её напрямую из действий — для этого есть `propagateAfterResult()`.

Четвёртое: **`Match.kickoffTbd === true` означает «время ещё не согласовано»**.
У такого матча в `kickoffAt` лежит дата тура и служебные 12:00 МСК — якорь для
сортировки и группировки по дням. Это время **нигде не показывается**: вместо
него выводится «время уточняется» (`formatTimeOrTbd` / `formatDateTimeOrTbd`
в `src/lib/format.ts`). Любой код, который проставляет матчу настоящее время,
обязан снять флаг. Делать `kickoffAt` необязательным нельзя: матчи без даты
исчезли бы из выборок по диапазону — с главной и из списка судьи.

Длительность тайма задаёт турнир, но дивизион может её переопределить
(`Division.halfDurationMin`, `null` — «как в турнире»): в одном турнире 8×8 и
6×6 играют разное время. Считай только через `halfDurationOf()` из
`src/lib/football.ts`, иначе табло судьи и подписи на сайте разойдутся.

Пятое: **матч учитывается в таблице того дивизиона, что записан в
`Match.divisionId`** — а не там, где команды числятся сейчас. Это то, что
позволяет разделить дивизион на верхнюю и нижнюю половину: команды уезжают в
половины, а матчи первого этапа остаются у предка, и его таблица живёт как
архив. У матчей без дивизиона работает прежнее правило («обе команды в одном
дивизионе») — иначе сломались бы лиги без дивизионов.

Перенос очков при разделении **нигде не хранится**: `getTournamentStandings`
считает предков раньше потомков и передаёт готовые числа в `computeStandings`
четвёртым аргументом (`carryOver`). Перенесённые очки уже включают
`pointsAdjustment` — прибавлять его второй раз нельзя.

Шестое: **сезон — это отдельный `Tournament`**, а `TournamentSeries` только
связывает сезоны в одну историю. У каждого сезона свой состав, регламент и
календарь; общего между годами — `Team.id` и `Player.id`. Сводка серии
(`src/lib/series.ts`) делает три запроса независимо от числа сезонов и считает
чистыми функциями — `getTournamentStandings` там не переиспользуется, иначе на
десяти сезонах вышло бы тридцать запросов. Титулы засчитываются только по
завершённым сезонам, иначе лидер текущего получит титул задним числом.

В круговую таблицу идут только матчи `stage: "REGULAR"` (`TABLE_STAGES`), а вот
в статистику игроков — все. Это не оплошность: таблица реализует регламент
кругового турнира, а бомбардиры считают все голы турнира.

## Структура

```
prisma/
  schema.prisma      модель данных (комментарии внутри)
  migrations/        история схемы, применяется через migrate deploy
  seed.ts            демо-данные, строятся относительно текущей даты
src/
  app/               маршруты (папка = URL)
    page.tsx           главная: матчи по дням
    tournaments/       турниры: таблица, расписание, бомбардиры, команды
    series/            история турнира по годам: сезоны, чемпионы, бомбардиры
    matches/[id]/      страница матча: хроника, составы, live-обновление
    teams/, players/, stats/
    referee/           консоль судьи (мобильная)
    captain/           кабинет капитана: заявка состава
    admin/             управление всем
  components/        общие компоненты; admin/ — формы админки
  lib/
    football.ts        ЧИСТАЯ футбольная логика: счёт, таблица, часы, словари
    stats.ts           расчёт статистики (обращается к базе)
    queries.ts         общие Prisma-выборки (matchCardArgs и т. п.)
    schedule-table.ts  ЧИСТЫЙ разбор и сборка таблицы расписания (Excel/CSV)
    series.ts          история серии по годам: сезоны, чемпионы, сводка команд
    auth.ts            вход, роли, проверки прав (только сервер)
    session.ts         JWT — БЕЗ Prisma и bcrypt, используется в middleware
    format.ts          даты и время, везде московское
    prisma.ts          подключение к базе
  server/            серверные действия ("use server"): запись в базу
    match-actions.ts   протокол матча
    admin-actions.ts   турниры, команды, игроки, площадки, аккаунты
    schedule-actions.ts генератор расписания, правка туров, импорт из таблицы
    playoff-actions.ts конструктор сетки
    playoff.ts         подстановка участников в сетку
  middleware.ts      первый рубеж защиты закрытых разделов
```

### Куда что класть

* Чистая футбольная логика без обращений к базе → `src/lib/football.ts`.
  Так её можно звать и на сервере, и в браузере.
* Любая запись в базу → серверное действие в `src/server/`. Не пиши в базу
  из компонентов страниц.
* Повторяющаяся Prisma-выборка полей матча → `matchCardArgs` в
  `src/lib/queries.ts`, чтобы карточка матча везде показывала одно и то же.

## Права доступа

Проверка в два слоя, оба обязательны:

1. `src/middleware.ts` — по префиксу пути и роли из токена. Быстро, но знает
   только роль.
2. Страница и серверное действие — проверяют ещё раз по базе. Middleware не
   знает, назначен ли этот судья на этот конкретный матч.

**Каждое новое серверное действие обязано само проверять права.** Образцы:
`loadEditableMatch()` в `match-actions.ts`, `requireAdminUser()` и
`canManageRoster()` в `admin-actions.ts`. Организатор проходит везде, где
проходит судья или капитан.

Значимые изменения пишутся в `AuditLog` — для лиги важно видеть, кто правил
результат после матча.

## Соглашения

* **Язык.** Все тексты интерфейса, сообщения об ошибках и комментарии — русские.
  Названия переменных и функций — английские.
* **Время.** Только московское, через `src/lib/format.ts`. Не вызывай
  `toLocaleString()` напрямую: сервер и браузер дадут разный результат и
  сломают гидратацию. Для полей формы — `toDateTimeInput` / `fromDateTimeInput`.
* **Цвета.** Только токены Tailwind из `globals.css`: `bg-surface`, `text-muted`,
  `text-live`, `border-border` и т. д. Они сами переключаются между светлой и
  тёмной темой. Не пиши `dark:`-варианты и хардкод вроде `bg-white`.
* **Компоненты.** По умолчанию серверные. `"use client"` — только там, где
  нужны состояние, эффекты или обработчики.
* **Формы админки.** Оборачивай в `ActionForm` (`src/components/admin/`),
  действие передавай через `.bind(null, id)`. Она сама показывает ошибку,
  успех и блокирует кнопку.
* **Результат действия.** Серверные действия возвращают `ActionResult`
  (`{ok: true} | {ok: false, error}`) или `FormState` (`{error?, message?}`) —
  и никогда не бросают исключение пользователю в лицо.
* **Множественное число.** Русские окончания — через `pluralize()` из
  `format.ts`, а не «5 матч(ей)».
* **Игровой номер игрока необязателен.** Не помечай поле `required`, а списки
  сортируй через `rosterOrderBy` из `queries.ts` — иначе безномерные игроки
  идут в произвольном порядке.
* **Права судьи не ограничивай назначением.** `canEditMatch` намеренно
  разрешает любому судье вести любой матч; принадлежность матча показывает
  `isAssignedReferee` и только для пометок в интерфейсе.
* **Папки на `_`** в `src/app/` исключаются из маршрутизации — не называй так
  каталоги маршрутов.

## Работа с базой

* Схема меняется только через `prisma/schema.prisma` + миграцию. Не правь
  таблицы руками в `psql`.
* Ограничения, которые Prisma не умеет выразить (`CHECK`), лежат отдельной
  миграцией `20250101000001_add_check_constraints`. Новые добавляй так же —
  отдельным SQL-файлом миграции.
* `npm run db:migrate` требует у пользователя базы прав `CREATEDB` для
  теневой базы. Если прав нет — генерируй SQL через
  `prisma migrate diff --from-empty --to-schema-datamodel` и применяй
  через `prisma migrate deploy`.
* `npm run db:seed` **удаляет все данные**. Не запускай на боевой базе.

## Проверка изменений

Минимум перед тем, как считать задачу сделанной:

1. `npm run typecheck` — без ошибок;
2. `npm run build` — успешно (dev-сервер при этом остановлен);
3. затронутые страницы открываются и отдают 200.

Автотестов в проекте нет. Если проверяешь серверные действия временным
маршрутом или скриптом — удали его после прогона.

Владелец проекта — не профессиональный разработчик. Поэтому:

* объясняй решения простым языком и по-русски;
* предпочитай понятный код хитрому;
* комментируй **почему**, а не **что** делает код;
* не тащи новые зависимости без внятной причины.
